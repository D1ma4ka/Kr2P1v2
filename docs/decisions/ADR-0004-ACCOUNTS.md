# ADR-0004 — P3: аккаунты и профиль

Статус: принято в разрешённом P3. Backend Fastify/PostgreSQL P2 сохранён.

Альтернативы: внешний identity SaaS требует интеграции/договоров; собственные
пароли и SMTP используют существующую БД, не требуют покупки сервиса. Выбран
второй вариант. Пароль 12–128 символов, scrypt N32768/r8/p1, случайная соль,
constant-time compare, одинаковая KDF-работа для отсутствующего аккаунта.
Одновременно максимум четыре KDF; SQL-бюджеты по IP и хешированному identity,
ограниченные почтовые resend. TTL кода 30 минут, одна операция/код; отправка
через SMTP перед commit, ошибка SMTP откатывает изменение. Dev/test письма
только в Mailpit и `example.invalid`. Production SMTP конфигурируется отдельно
с явным включением delivery, auth и обязательным TLS; в P3 не включается.

Access bearer 1 час, refresh 30 дней; случайные 256-bit значения, в БД SHA-256.
Refresh одноразовый, ротация атомарна; повтор использованного refresh отзывает
все сессии аккаунта (строгая политика; клиент сериализует refresh). Сброс пароля
также отзывает все сессии. Выход отзывает текущую сессию и её refresh. P2 dev
сессии остаются до исходного TTL. Стабильный UUID не зависит от платформы.
Все поля/TTL/error schema опубликованы в общем OpenAPI: iOS использует тот же
API, Android-идентификаторов/платформенных полей нет.

18+ — явная декларация пользователя в UI и обязательный `adultConfirmed=true`
в API. Это age gate, не документальная проверка возраста; юридическая оценка
метода до публичного запуска остаётся обязательной.

Профиль по умолчанию private. Owner видит всё; public и friends применяются
на сервере, friends проверяет принятую связь P2. Пол имеет отдельную видимость;
каждая HTTPS-ссылка — собственную. Avatar/cover наследуют ACL профиля;
прямой media URL повторно проверяет ACL, hidden/deleted недоступны. Чужое
прикрепление запрещено owner FK и проверкой live asset. Версия профиля защищает
от перезаписи конфликтов; DTO P2 дополняется совместимыми optional полями input.

Запрос удаления хранится в SQL с дедлайном 30 дней, немедленно блокирует доступ,
публичность и сессии. Это запрос на удаление, не фиктивное подтверждение полного
стирания. До эксплуатации требуется операционный процесс исполнения срока и
юридические правила retention/backups (P8/P9); production ещё не развёрнут.

Логирование не содержит email/password/token/body/query. Bearer только в header,
код из письма вводится в приложение; HTTP deep links с токеном не нужны.
