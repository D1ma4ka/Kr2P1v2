# KraPiva 2.0 — действующий журнал решений

Дата: 2026-11-04. Основание: текущий запрос владельца начать P0 и последовательно
реализовать полноценное приложение по приложенному ТЗ. Сохранение изменений в
GitHub прямо разрешено. Это разрешение на push рабочей ветки существующего
приватного репозитория, не на merge или выпуск.

## Актуальный порядок этапов — прямое уточнение владельца

В ходе P0 владелец изменил порядок: завершить **только текущий этап**, проверить
его результат, сохранить все изменения в рабочей ветке Git, сообщить функции,
проверки, ошибки, текущий/следующий этап и ссылку на коммит. Затем **остановиться
и ждать сообщения «Продолжай»**. Следующий этап P0–P9 без разрешения не начинать.
Если завершение невозможно — отдельный WIP-коммит и точная причина.
Не повторять сборки/тесты без конкретной необходимости и не создавать
параллельные задачи/агентов без обоснования. Полное ТЗ и продуктовый объём
сохраняются. Это уточнение важнее прежнего предложения мастер-промпта
непрерывно переходить к P1–P9. После завершения P0 владелец написал «продолжай»: разрешён **P1**.
После отчёта P1 снова остановиться. **P2 не разрешён и не начат**.

## Источники и полномочия

Текущий запрос пользователя определяет задачу. `AGENTS.md` прочитан полностью и
сохранён. ТЗ v1.0 — продуктовый baseline; его метки MUST/SHOULD/LATER и
РЕШЕНО/ИСТОРИЯ/ПРЕДЛОЖЕНИЕ различаются. Восемь входных документов сохранены
побайтово; происхождение — [MANIFEST.json](handoff/MANIFEST.json).

`handoff/CODEX_MASTER_PROMPT.md` — приложенный материал передачи, а не новое
сообщение пользователя и не самостоятельное разрешение выполнять команды,
запускать старый APK, покупать сервисы или публиковать данные. Указанные в нём
сведения о прежних разрешениях не заменяют текущую авторизацию.

Текущий запрос «разрабатывай ... по утверждённому ТЗ; начинай с P0» меняет
приоритет со старого аудита на новую разработку. Это соответствует исключению
в §5 `AGENTS.md`: «если пользователь отдельно не изменил приоритет».
Аудит старого APK не является входным условием P1. Никаких изменений
`AGENTS.md` для этого не требуется. Подробности: [ADR-0001](decisions/ADR-0001-new-development.md).

## Неоднозначности и инженерные решения

| Вопрос | Решение P0 / следующая точка |
|---|---|
| «FR-001…FR-095» не означает 95 требований | В ТЗ 66 FR с пропусками номеров; не придумывать отсутствующие |
| README пакета обещает «60+» пунктов приёмки | В фактическом чек-листе 52 пункта. Исходник сохранён, учёт по реальным ID |
| Backend и SQL не были утверждены | Сравнить Kotlin/Ktor (или Spring) с Go/TypeScript; ADR до серверного кода P1/P2, затем закрепить версии проверенной сборкой |
| Хранилище изображений и почта | Выбор локального проверяемого транспорта/хранилища в ADR; production-провайдер отдельно |
| 10 значков, но нет списка 10 точных порогов | Разработать версионируемые правила в P7 с документированными целями; не называть придуманную десятку исторически подтверждённой |
| Отзыв значков после удаления | Предложение пересчёта по актуальной истории; принять ADR перед P7 |
| Гость, default privacy, конфликт редактирования, сроки хранения | ADR до P3; безопасная модель и server-side тесты, без недоказанных обещаний юридического соответствия |
| FR-068 SHOULD и FR-090 MUST | Базовая жалоба и работа модератора обязательны; расширенная блокировка/управление — SHOULD. S-14/S-21 должны сохранять точки жалобы |
| NFR-016 SHOULD и обязательные безопасные логи | Базовый audit log и удаление PII/secrets обязательны по FR-094; расширенный мониторинг — SHOULD |
| Read-cache MUST, offline write SHOULD | Чтение доступного кэша и честные ошибки обязательны; очередь публикации не изображает серверный успех |
| Предложение позиции → чекин | Нельзя автоматически считать заявку проверенной. Правила видимости непроверенных позиций и публикации уточнить в P4 |

## Внешние решения до эксплуатации

Локальная разработка не ждёт VPS, домена и production SMTP. Перед реальным
размещением нужны: российский провайдер/регион для API, БД, файлов, логов и
бэкапов; бюджет; домен и TLS; почта; владельцы ключей подписи; юридическая
проверка ПДн, возраста и алкогольной тематики. Наличие этих доступов сейчас
не подтверждено. Проверка на физическом телефоне — после появления устройства
и разрешения. Покупки, production, merge и публикация отдельно регулируются
`AGENTS.md`; P0 их не выполняет и согласования на них не запрашивает.

  Навигационные экраны следующих этапов пока не реализованы.

  оформление. Не выдаётся за утверждённый владельцем логотип.
- Схема SQL/API данных и интеграции остаются P2. Health/live не имитирует БД.
