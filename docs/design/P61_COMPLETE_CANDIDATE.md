## Серверная защита кода

Добавлена только совместимая миграция `009_email_verification_codes.sql` и endpoint `POST /v1/auth/verify-code` (`email`, `code`). Существующие `/verify`, `/resend`, `/forgot-password` и reset/session API сохранены, OpenAPI обновлён.

Код криптографически случайный, шесть ASCII-цифр включая ведущие нули; хранится salted scrypt hash, не plaintext. Срок 10 минут, максимум пять догадок на выдачу. Счётчик ошибок коммитится, user-first row lock сериализует конкурентные попытки. Работают IP/identity budgets, minute cooldown и замена прежнего кода при resend. Успех любого способа подтверждения инвалидирует альтернативный credential; ошибки не раскрывают наличие аккаунта. Старый 256-битный credential для прежних клиентов сохраняет прежний контракт/срок.

Перед миграцией текущей локальной БД сделан ignored `work/p61-complete/before-009.dump`; миграция успешно применена, существующие volumes/данные сохранены. Новый backend запущен локально. Реально проверены HTTP → SMTP/Mailpit → numeric verification → login и отказ повтора. Письма наружу не отправлялись, используются только synthetic `@example.invalid`.

## Отклонения и ограничения до визуальной приёмки

- Фотореалистичный бокал/пена макета заменены локальной программно рисуемой иллюстрацией с анимацией; это **не** фотографически точная копия PNG. Полные mockup-изображения в качестве UI не используются.
- Настройки заменяют неработающий колокольчик. Нет фальшивых уведомлений или будущих P7-маршрутов.
- Стили приходят с сервера, не захардкожены как IPA/лагер/стаут; числа/сорта/фотографии из макетов не подставляются. Каталоговый рейтинг — агрегат доступных данному пользователю записей, это отмечено в UI, а не выдуманная глобальная оценка.
- API чекина не содержит ABV: в карточках чекинов он не выдумывается. Верхняя граница друзей показывается как `50+` при следующей странице, поскольку API не возвращает total.
- Контролы ввода/видимости/дополнительных полей адаптированы под реальные правила и доступность. Фактические размеры/переносы/контраст на телефоне ещё не проверены; pixel-perfect соответствие не заявляется.
- Full emulator suites имеют прежние изоляционные guards и местами адрес `10.0.2.2`; **не запускать их целиком на личном телефоне**. Для phone candidate сначала manual/адресная проверка; UI assertions не отключались. Существующий HomeIntegrationTest не покрывает весь П6.1.

## Получение и запуск кандидата после реализации

Локальные APK, не включены в Git:

```text
work/p61-complete/krapiva-p61-complete-debug.apk
work/p61-complete/krapiva-p61-complete-tests.apk
```

Это debug `ru.krapiva.app.debug`, Android 8.0+, не release. API задан как `http://127.0.0.1:53000/` для USB reverse. APK сам по себе не содержит backend. На компьютере, к которому подключён телефон, должен работать **этот же обновлённый локальный backend с миграцией 009**. Облачный сервер на loopback этим USB-туннелем не достигается. Инструкции backend — `android/README.md`; на новом checkout `.env` создаётся только при отсутствии, существующие данные и fixtures повторно не создавать.

После готовности локального API на компьютере и разрешения USB debugging пользователем:

```sh
adb devices -l
adb reverse tcp:53000 tcp:53000
adb install -r /absolute/path/krapiva-p61-complete-debug.apk
adb shell am start -n ru.krapiva.app.debug/ru.krapiva.app.MainActivity
```

При нескольких устройствах указывать конкретный `adb -s SERIAL`. При несовпадении прежней подписи не удалять приложение/данные ради установки; выбрать отдельный тестовый профиль/устройство либо сохранить совместимую signing-конфигурацию. Credentials, `.env`, fixture JSON, signing keys и backups в чат/Git не отправлять.
