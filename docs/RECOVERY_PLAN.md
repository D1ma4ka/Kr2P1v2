# План исследования и карта артефактов

Работа пока остановлена перед первым исследованием APK. Этот план не сообщает
о выполнении перечисленных операций.

## Последовательность

1. Получить оригинал, сохранить отдельно, зафиксировать размер и SHA-256.
   Проверить ZIP, признаки самостоятельной APK и возможную потребность в splits.
2. Выполнить `tools/apk_inventory.py`. Это только список ZIP-записей и хеш;
   двоичный AndroidManifest и DEX он не декодирует, подпись не проверяет.
3. Проверить версии доступных JADX, Apktool и Android SDK tools; установить
   недостающее разрешённым способом. Сохранить команды, версии и ошибки.
4. Декодировать ресурсы, манифест и smali через Apktool; сохранить полный вывод
   отдельно. Получить доступное DEX-представление через JADX. Выбирать фактический
   способ исследования по стеку, а не по желаемой технологии новой версии.
5. Установить package name, версию, SDK, компоненты, разрешения, сертификат,
   зависимости и архитектуру. Неполную декомпиляцию дополнять smali/DEX.
6. Проследить точки входа, экраны и маршруты, камеру/штрихкоды, хранилища,
   каталог, поиск, чекины, статистику, сеть и резервные копии. Присутствие
   строки или класса не считать подтверждением доступной функции.
7. Прочитать встроенные базы в режиме только чтения; зафиксировать схему,
   индексы, связи, число строк и происхождение данных, насколько оно доказуемо.
8. Отделить код приложения от сторонних библиотек и сгенерированных файлов.
   Сохранить лицензионные уведомления. Проверить кандидатов на импорт на секреты,
   персональные данные, размер и права публикации.
9. Оценить материалы для сборки. Существующий Gradle-проект проверять первым.
   При достаточных материалах выполнить ограниченную попытку восстановления,
   явно отделяя извлечённое, выведенное и созданное заново. Apktool-rebuild
   и Gradle-сборку учитывать отдельно. Не подменять восстановление пустым приложением.
10. При возможности успешной сборки записать команду, версии среды, размер и
    SHA-256 результата. Статический этап не включает установку или запуск APK;
    переход к динамическому исследованию согласуется отдельно по AGENTS.md.
11. Повторно проверить SHA-256 оригинала, diff и список публикуемых файлов.
    Обновить отчёты, сохранить коммиты в рабочей ветке и draft PR.

## Размещение материалов

| Артефакт | Путь | Хранение |
| --- | --- | --- |
| Неизменённая APK | `input/krapiva-0.2.0-local.apk` | Локально, исключена из Git |
| Первичная инвентаризация | `work/inventory.json` | Локально; проверить перед использованием в отчётах |
| Полный вывод и логи инструментов | `work/raw/<sha256>/` | Локально, отдельно от редактируемых материалов |
| Результаты Apktool | `work/raw/<sha256>/apktool/` | Необработанный результат |
| Результаты JADX | `work/raw/<sha256>/jadx/` | Необработанное декомпилированное представление |
| Проверенные ресурсы/манифест | `legacy/decoded/` | Выборочный импорт после проверки |
| Проверенный код приложения | `legacy/decompiled/` | Явно обозначить декомпиляцию, не оригинальные исходники |
| Схема и измерения данных | `audit/06-database-and-search.md` | Доказательства и агрегаты, без приватных строк |
| Сводный анализ | `docs/APK_ANALYSIS.md` | Обновлять по фактическим находкам |
| Текущий статус и воспроизведение | `docs/RECOVERY_STATUS.md`, `tools/README.md` | Поддерживать после этапов |

После получения APK создавать тематические отчёты AGENTS.md:
`audit/01-apk-inventory.md`, `02-manifest-and-permissions.md`,
`03-architecture-and-code.md`, `04-screens-and-navigation.md`,
`05-barcode-scanner-and-camera.md`, `06-database-and-search.md`,
`07-network-and-integrations.md`, `08-storage-and-backup.md`, `09-feature-inventory.md`.

`docs/technical-specification.md`, `docs/architecture-proposal.md` и существенные
ADR готовятся на основе результатов исследования; сейчас они не создаются
как якобы восстановленные требования или утверждённая архитектура.
