# P8.6 · Протокол приёмки Smart Bar

22 ноября 2026. Ветка `codex/krapiva-p8.6-smart-bar`, исходники и тесты `d72f5eee05b430a99c34a05ca79011ab1266c105`. Локальные Fastify, PostgreSQL 17 и Mailpit. Каждый прогон создаёт отдельную базу со случайным именем. В данных только синтетические позиции, места и аккаунты. Журналы теста содержат длительности и результаты проверок.

## Пользовательский маршрут

Один тест прошёл путь от входа до повторного ранжирования через TCP на loopback. Kotlin-клиент теста разбирает тела теми же функциями, которыми пользуется экран. Состояние Android Activity, Compose, Keystore и SQLite в этот прогон не входят. ## Цена чтения и расчёта

Для непустого меню тестовый клиент выполнил один GET полного меню и один GET истории. Применение пяти тем, сравнение и ранжирование сохранили счётчик HTTP без изменений. В коде экрана этим чтениям соответствуют два эффекта. Пустое опубликованное меню больше не инициирует чтение истории. Счётчик относится к стенду, трафик Activity на устройстве не снимался. Запросы карты, намеренное открытие карточки, сохранение чекина, сетевые повторы и обновление имеют отдельную стоимость.

На локальном стенде одно начальное чтение с декодированием заняло 225,6 мс для 250 строк и 91,2 мс для 100 чекинов. Для вычислений выполнено пять прогревов и 40 измерений в JVM. Фильтрация «Мои IPA» дала медиану 0,95 мс и p95 4,17 мс. Построение профиля и ранжирование всех 250 кандидатов дали 3,08 и 10,21 мс соответственно. Это один процесс без конкурентной пользовательской нагрузки. Время кадра на Android и характеристики сервера под многопользовательской нагрузкой не измерялись.

## Как повторить на стенде

Собрать backend через `npm run build` в `backend/`. Поднять изолированные PostgreSQL и Mailpit, передать локальные `TEST_DATABASE_URL`, `DATABASE_URL`, `SMTP_HOST`, `SMTP_PORT`, `MAILPIT_API_URL` через окружение и выполнить там `npm test`. Для сквозного JVM-теста указать абсолютный путь к собранному `backend/` в `KRAPIVA_SMART_BAR_TEST_BACKEND`. Из `android/` запустить `./gradlew testDebugUnitTest assembleDebug assembleDebugAndroidTest lintDebug`. Без этой переменной сквозной тест помечается skipped. Проверить число пропусков в JUnit XML. Инструментальные сценарии требуют отдельного изолированного устройства.

## Оставшийся прогон на устройстве

1. На API 26 и 33+ войти тестовым аккаунтом, выбрать город вручную, открыть A на карте и пройти маршрут из первой таблицы. Проверить обе упаковки с одинаковым именем, удалить и вернуть одну из четырёх выбранных позиций.
2. Перейти в карточку и редактор, опубликовать чекин и вернуться. Проверить сохранение правил и выбора, смену статуса и объяснения Advisor. Быстро сменить заведение и фильтр, затем повторить после сворачивания.
3. На 320 dp и 150% пройти этот путь в LIGHT/DARK и после системного переключения. С TalkBack проверить название позиции, упаковку, состояние выбора, последовательность фокуса и достижимость действий.
4. Проверить пустую публикацию, соединение с задержкой, отключение сети после прогрева, публикацию старше суток, истечение TTL, перезапуск и вход вторым аккаунтом. Сверить дату и источник меню и отсутствие чужих правил/оценок. Отметить API, SHA APK и фактический результат каждого шага.
