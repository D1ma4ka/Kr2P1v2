## 1. Публикация и минимальный сервер

Предлагается одна текущая опубликованная редакция на проверенное заведение. PostgreSQL хранит заголовок `venue_menus(venue_id PK/FK, revision bigint, published_at timestamptz, source text, published_by FK users)` и строки `venue_menu_items(venue_id FK, position_id FK, ordinal, PRIMARY KEY(venue_id,position_id), UNIQUE(venue_id,ordinal))`. Целостность каталога сохраняют внешние ключи без каскадного удаления позиций. Наличие строки означает «в опубликованном меню на дату», без обещания остатка в реальном времени.

Минимальный канал записи — авторизованная операция модератора Fastify `PUT /v1/moderation/venues/{id}/menu` с expectedRevision (0 для первой публикации), источником, упорядоченным полным списком. Проверить полномочия существующим механизмом, источник, verified заведение, verified канонические позиции и пивоварни, дубли после разрешения alias, лимит 250 позиций (проектный предел). Замена строк, проверка версии и аудит автора в одной транзакции под блокировкой строки venues, включая первую публикацию. Устаревшая версия — 409; после потерянного ответа перечитать revision и содержимое перед повтором. Некорректный пакет отклонить целиком. Источник для посетителя — публичная атрибуция без личных контактов.

Чтение `GET /v1/venues/{id}/menu` по действующим правилам доступа к местам: один согласованный SQL-снимок заголовка и строк, revision, publishedAt, source, items с ordinal, canonical positionId, releaseId, breweryId/name, styleId/name, name, packaging, volumeMl, abv, ibu. После модерации при чтении исключить скрытые/неверифицированные позиции и пивоварни, слитые строки потребуют перепубликации. Неподтверждённое место недоступно. Для доступного места различить отсутствие публикации (200, menu=null) и опубликованный пустой список (200, items=[]). Повторное чтение получает актуальные поля каталога даже при прежней revision. Один полный ответ до 250 строк позволяет комбинировать правила на всём наборе, без запросов деталей на каждую строку. Каталог остаётся постраничным. Достаточны миграция, две операции, OpenAPI, авторизованный ввод из проверенного источника и интеграционные тесты. Кабинет заведения, POS, биллинг и отдельный сервис рекомендаций не требуются.

## 2. Универсальные правила

FilterSpec v1 — переносимый JSON с version, styleIds[], breweryIds[], packaging[], familyIds[], диапазонами abv/ibu/volumeMl (min/max), q, novelty и sort. Пример: `{"version":1,"styleIds":[],"packaging":["can","bottle"],"abv":{"max":5},"sort":"name"}`. Пространство поиска задаёт вызов (меню конкретного заведения либо каталог). Внутри списка — OR, между разными полями — AND, пустой список снимает ограничение. Семейство разворачивается в свои styleId по версионированному отображению. Если выбраны одновременно семейства и стили, применяется пересечение. Числовые границы включительные, null не проходит активный диапазон. Пустой q пропускается, иначе нормализовать NFKC, регистр, пробелы и искать все токены в имени/пивоварне/стиле. Зафиксировать совпадения кириллицы общими примерами. Некорректные единицы, min > max, неизвестная версия дают видимую ошибку. Сортировка по умолчанию для меню — ordinal, затем positionId; для имени — нормализованный текст, затем ID, для ABV — по возрастанию, null в конце. Сравнивать ID в канонической строковой форме.

На Android чистая функция получает полный снимок и отдельный контекст владельца. На сервере адаптер каталога компилирует поддержанные поля в параметризованные предикаты до LIMIT. Неподдерживаемое условие недоступно в данном контексте; сохранённое правило с таким полем нельзя молча ослабить. При расширении каталога новые параметры/версия схемы аддитивны, существующие запросы сохраняют семантику. Один набор JSON-векторов фиксирует результат для Kotlin, SQL и будущего iOS.

## 3. Сценарии и сохранение

Пять начальных действий разворачиваются в редактируемые условия: «До 5%» (abv.max=5), «До 25 IBU» (ibu.max=25), «В банке» (packaging=can), «Из любимых стилей» (styleIds с положительным предпочтением из §5), «Новое для меня» (позиция отсутствует в окне §5). Подпись последнего — «По последним N чекинам». Для пустой истории или пустого множества любимых стилей пояснить нехватку данных и не подставлять пустой OR как все стили. Сохранённый персональный сценарий хранит тип условия, чтобы предпочтения вычислялись заново. Явный ручной выбор стилей сохраняет конкретные ID.

Отдельный локальный документ smart-bar-filters-v1, атомарная запись через AccountApi. Запись: UUID, ownerUserId, название 1–80, version, spec, опциональный venueId для привязанного правила, updatedAt. Создание, изменение, переименование, применение и удаление по UUID. Не записывать выдачу или содержимое истории. Старый collections-v1 остаётся читаемым. У сменившего аккаунт пользователя свои правила и выбор сравнения.

## 4. Сравнение и минимальный интерфейс

Из существующей карточки места открыть «Меню», показать источник, дату, список с упаковкой, объёмом и переходом в карточку. Предусмотреть загрузку, отсутствие публикации, опубликованное пустое меню, пустой результат фильтра и ошибку с повтором. Для разрешённой локальной копии указывать дату получения и последнее известное состояние. Свежий ответ menu=null вытесняет сохранённый. Публикация в минимальном UI посетителя не нужна.

На экране меню доступны фильтры, сценарии, сохранение, персональные причины и выбор 2–4 строк. Ключ выбора — venueId и canonical positionId. Смена места очищает выбор; обновление меню пересекает его с актуальными ID. Пятый выбор объясняет лимит. Общие поля сравнения взять из снимка, личные оценки получить действующей статистикой только выбранных (до четырёх) и различать нет оценки, ошибку, кэш. На узком экране группировать значения с названием упаковки под каждым признаком. Отказ геолокации не мешает открыть уже выбранное заведение.

## 5. История и детерминированный подбор

Android получает окно через существующий аутентифицированный GET /v1/checkins?sort=date_desc&limit=50. Использовать nextCursor сервера без декодирования и с тем же sort; остановка при 100 разных checkin.id или null. Нормально это два запроса при 100+ записях. Одинаковые даты разделяет id DESC, время — occurred_at, не created_at. Записи одной позиции сохраняют кратность. В queries.where обязательны c.user_id из сессии, deleted_at IS NULL и hidden_at IS NULL; fingerprint включает diary:user и фильтры. Чужой cursor → 400, отсутствие токена → 401. Feed, общий профиль, кэш соседнего аккаунта и черновики не являются источниками окна.

На смене сессии отменить запросы, сбросить состояние, перед присвоением результата проверить идентификатор владельца и поколение сессии. Не сохранять тела, заметки и медиа в новом кэше ранжирования. Ошибка второй страницы, повтор курсора или потеря доступа не превращают частичные 50 в полную историю. При известных изменениях дневника перечитать окно с начала. Между HTTP-страницами нет транзакционного снимка: дедупликация ID защищает от повторов, но не гарантирует снимок при одновременном редактировании дат с другого устройства. Если требуется строгая моментальная согласованность, отдельный серверный owner-only SELECT с ORDER BY occurred_at DESC,id DESC LIMIT 100 решает её одним запросом.

Предлагаемая формула v1 работает на успешно загруженных N=1…100 записях и строках текущего меню после фильтра. Для каждого известного styleId и breweryId суммировать (ratingQuarters − 12) по оценённым записям данной группы; предпочтение P = trunc(100 × сумма / (число оценённых + 2)), округление к нулю. Сглаживание ограничивает эффект единичной оценки. Null не участвует в среднем, но учитывается в новизне. Нет оценок или ID — P=0. Новизна U=200 для выпуска вне окна, 100 для новой позиции известного выпуска, иначе 0. Это новизна относительно окна, без обещания «никогда не пробовали».

Базовый балл B = 2 × P(style) + P(brewery) + U. Последовательно выбрать до 10 разных positionId. Перед каждым выбором скорректировать B на −150 за каждую уже выбранную строку той же известной пивоварни и −100 за каждую того же известного стиля. Побеждает максимум, затем лексикографически меньший positionId. Причины выводить из действительных слагаемых: положительное предпочтение, новый выпуск или новая упаковка; без таких сигналов подписать «Из меню». При N=0 показать обычный порядок меню и приглашение вести дневник. При истории без оценок работают только новизна и разнообразие. Одинаковые входы дают одинаковый порядок на разных клиентах. Внешние AI API, сетевые модели и случайность не участвуют.
