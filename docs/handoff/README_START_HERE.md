# KraPiva 2.0 — пакет передачи OpenAI Codex

Дата: 4 ноября 2026 г. **Это ТЗ и исполняемые инструкции, не завершённая разработка.** Репозиторий GitHub не изменялся при подготовке пакета.

## Основные два файла

1. `docs/TECHNICAL_SPECIFICATION.md` — подробное ТЗ (продукт, роли, scope, FR/NFR, модель пивной позиции, экраны, backend, безопасность, план и Definition of Done).
2. `codex/CODEX_MASTER_PROMPT.md` — готовый полный промт для Codex.

## Дополнительно

- `docs/DECISIONS_AND_SCOPE.md` — все 9 свежих решений владельца, отдельно от инженерных предложений.
- `docs/ARCHITECTURE_BLUEPRINT.md` — схема, модули, ADR и правила API.
- `docs/SCREEN_MAP_AND_FLOWS.md` — маршрутная карта и варианты навигации.
- `docs/BRAND_BRIEF.md` — новый craft beer стиль, требования к реальному логотипу/иконке и запрет ботаники.
- `checklists/ACCEPTANCE_CHECKLIST.md` — 60+ проверяемых критериев.

## Как передать Codex

1. Открой существующий приватный репозиторий `D1ma4ka/Kr2P1v2` **в Codex**. Не создавай новый.
2. Прикрепи оба основных Markdown файла к задаче Codex (дополнительные документы тоже полезны). Если Codex работает только с файлами репозитория, разреши ему добавить их в **новую рабочую ветку** от `main`, не меняя `README.md` и `AGENTS.md` удалением.
3. Вставь полный текст `codex/CODEX_MASTER_PROMPT.md` как задачу Codex. По запросу входных материалов передай **этот пакет**, а не старую APK/SQLite/фото.
4. Сначала проверь в отчёте Codex, что он прочитал `AGENTS.md`, открыл `D1ma4ka/Kr2P1v2`, создал рабочую ветку, увидел актуальное содержимое `main` и не пытался восстановить legacy.
5. Затем отслеживай реальные коммиты, тесты, Android APK и backend E2E. На production deployment, покупку VPS, домена, отправку реальной почты, merge и публикацию давай отдельное разрешение только после понимания расходов/рисков.

## Особо важное уточнение

Ветка `main` во время предыдущей проверки содержала **только `README.md` и `AGENTS.md`**. Следовательно, операция «удалить всё старое из main, кроме этих двух файлов» может быть **пустой**. Есть другая ветка `recovery/legacy-apk`, её не надо сливать; сохранение истории Git не равнозначно импорту старого кода в новый продукт. Переписывать историю и уничтожать ветки не нужно для чистой разработки. Если требуется именно уничтожение удалённой архивной ветки и исторических Git-объектов, это отдельное потенциально необратимое действие с дополнительным согласованием.

## Исходные устаревшие материалы

Исторические архивы `krapiva-0.2.0-local.apk` и `krapiva-source-0.2.0.zip` изучались при подготовке ТЗ, но **не включены** в этот пакет намеренно. Не надо повторно переносить их в репозиторий. Старая база GTIN/картинок больше не является источником данных продукта 2.0.

## Блокеры, разрешаемые отдельно

Точные реквизиты сервера РФ, домена, исходящей почты, подписывающих ключей, бюджета инфраструктуры и юридическое заключение по алкогольной тематике не известны как утверждённые. Они **не блокируют** разработку и проверку системы локально / на staging в безопасных пределах; но без них нельзя честно считать публичную эксплуатацию полностью запущенной.
