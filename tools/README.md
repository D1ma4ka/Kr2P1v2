# Воспроизводимая первичная инвентаризация

`apk_inventory.py` использует только стандартную библиотеку Python 3.
Он читает файл, вычисляет SHA-256 до и после работы и перечисляет ZIP-записи.
Файлы из APK **не распаковываются и не выполняются**. Существующий JSON
и оригинальная APK не перезаписываются.

Из корня проекта после получения оригинала:

```sh
mkdir -p work
python3 tools/apk_inventory.py input/krapiva-0.2.0-local.apk --output work/inventory.json
```

Если `work/inventory.json` уже существует, выбрать новое имя результата.
JSON может содержать чувствительные имена файлов из архива; он хранится локально
и не должен автоматически попадать в Git. При передаче отчётов проверять его
содержимое так же, как остальные извлечённые материалы.

## Границы инструмента

- Наличие `AndroidManifest.xml` и `classes*.dex` видно по именам записей.
- `.db`/`.sqlite`/`.sqlite3` — только кандидаты по имени, без проверки формата.
- Размеры и CRC в JSON взяты из ZIP-метаданных; CRC содержимого не проверяется.
- Не декодируются манифест, ресурсы, DEX, versionName или package name.
- Не проверяются криптографическая подпись, совместимость и комплектность splits.
- Не определяются реализованные функции, архитектура или возможность сборки.
- Подозрительные пути и повторяющиеся имена отмечаются; никакие записи не извлекаются.

Следующие инструменты выбираются после получения APK: JADX, Apktool,
`apkanalyzer`/`aapt` и `apksigner`, SQLite в режиме только чтения. Их фактические
версии и команды нужно записать перед исследованием. Сейчас они не запускались;
Android SDK, необходимые пакеты и точные версии ещё не подобраны.

## Проверки вспомогательного скрипта

```sh
python3 -m unittest discover -s tools/tests -v
```

Пять проверок используют искусственные ZIP-файлы: неизменность входного файла,
отсутствие чтения содержимого ZIP-записей, повторяющиеся/опасные имена, некорректный
архив, запрет перезаписи, изменение исходника во время сканирования. Это проверки
инструмента, а не APK, Gradle-сборки или поведения приложения.
